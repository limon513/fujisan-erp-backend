# 05 — Demo / Staging Deployment (Neon + Render + Vercel)

> **Temporary showcase environment** for demonstrating progress to clients. Production for each
> client is a VPS with Docker Compose, Nginx and Postgres (see `02-architecture.md` §9); nothing
> here is specific to these providers, so moving later is just a change of environment variables.
>
> Use demo data only — never load a client's real customers, payments or NID documents here.

```
Browser ──► Vercel (Next.js) ──/api/* rewrite──► Render (Express API) ──► Neon (PostgreSQL)
```

The browser only ever talks to the Vercel domain. Vercel forwards `/api/*` to Render, so the
refresh-token cookie is first-party (no cross-site cookie settings, no CORS for the app itself).

## 1. Neon (database)

1. Use the existing project (AWS us-east-2). Render's `render.yaml` uses the matching region
   (`ohio`) so queries stay fast. (For a long-lived Bangladesh deployment, Singapore is closer.)
2. Copy two connection strings from _Connect_:
   - **Pooled** (host contains `-pooler`) → `DATABASE_URL`
   - **Direct** (no `-pooler`) → `DIRECT_DATABASE_URL` (migrations need a direct connection)
3. Keep your local `.env` pointed at local Postgres. Development commands (new migrations,
   experiments) would otherwise change the demo database the client is looking at. To seed or
   inspect the demo DB from your machine, pass the URL just for that command:
   `DATABASE_URL="<neon pooled url>" DIRECT_DATABASE_URL="<neon direct url>" npm run db:seed`

## 2. Render (backend)

1. Dashboard → **New → Blueprint** → select `fujisan-erp-backend`. It reads `render.yaml`.
2. Fill in the prompted values: `DATABASE_URL`, `DIRECT_DATABASE_URL`, `CORS_ORIGINS`
   (your Vercel URL), `SEED_ADMIN_PASSWORD` (strong; you'll be asked to change it on first login).
   `JWT_ACCESS_SECRET` is generated by Render.
3. Deploy. Each start runs `prisma migrate deploy` → idempotent seed → server.
4. Check `https://<service>.onrender.com/api/v1/health` and `/api/docs`.

Notes:

- Free plan sleeps after ~15 min idle; the first request then takes ~30–60 s. Open the site a minute
  before a client demo to wake it up.
- `TRUST_PROXY=2` (Vercel + Render). After the first login, check _My login history_ shows your
  real public IP; if it shows a Vercel/Render address, adjust `TRUST_PROXY`.

### File storage (Neon storage or Cloudflare R2)

Uploaded files (plot layout images, documents) can't live on Render's disk — it's wiped on every
deploy. Use any private S3-compatible bucket. The demo uses **Neon storage** (same Neon project):

| Render variable                               | Value                                                                         |
| --------------------------------------------- | ----------------------------------------------------------------------------- |
| `STORAGE_DRIVER`                              | `s3`                                                                          |
| `S3_BUCKET`                                   | `uploads` (the bucket must already exist)                                     |
| `AWS_ENDPOINT_URL_S3`                         | from Neon → Storage (e.g. `https://br-….storage.c-6.us-east-2.aws.neon.tech`) |
| `AWS_REGION`                                  | `us-east-2`                                                                   |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | a Neon storage credential                                                     |

The backend accepts either these standard `AWS_*` names (paste Neon's block as-is) or
`S3_ENDPOINT` / `S3_REGION` / `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY`.

Cloudflare R2 works the same way: endpoint `https://<account-id>.r2.cloudflarestorage.com`,
region `auto`, and an R2 API token with read/write on the bucket.

### Email (password reset codes, later notifications)

The demo sends mail through **Resend**'s HTTP API:

| Render variable  | Value                                                                      |
| ---------------- | -------------------------------------------------------------------------- |
| `RESEND_API_KEY` | the Resend API key (`re_…`)                                                |
| `MAIL_FROM`      | `Fujisan ERP <onboarding@resend.dev>` until a domain is verified in Resend |

Without a verified domain Resend only delivers to the Resend account owner's address. For a client,
verify their domain in Resend and set `MAIL_FROM` to e.g. `Fujisan ERP <no-reply@their-domain>`.
With no `RESEND_API_KEY` the backend falls back to SMTP (`SMTP_HOST`…), then to logging the email.

Files are always served through the API with short-lived signed links, so the bucket never needs
public access.

## 3. Vercel (frontend)

1. **Add New → Project** → import `fujisan-erp-frontend` (framework auto-detected: Next.js).
2. Environment variables (Production + Preview):
   - `BACKEND_URL` = `https://<service>.onrender.com` (no trailing slash)
   - `NEXT_PUBLIC_APP_NAME` = `Fujisan ERP`
   - `NEXT_PUBLIC_COMPANY_NAME` = `Fujisan Properties Ltd.`
3. Deploy. Rewrites are evaluated at build time, so **redeploy after changing `BACKEND_URL`**.
4. Put the Vercel URL into Render's `CORS_ORIGINS` (only needed for tools calling the API
   cross-origin; the app itself goes through the rewrite).

## Developing against the demo (current setup)

Development and the demo share the Neon database and Neon storage, so whatever is entered while
building is there to show clients. The local `.env` therefore has:

| Variable                 | Value                                                         |
| ------------------------ | ------------------------------------------------------------- |
| `DATABASE_URL`           | Neon pooled URL                                               |
| `DIRECT_DATABASE_URL`    | Neon direct URL (host without `-pooler`)                      |
| `MIGRATION_DATABASE_URL` | local Postgres (`fujisan_erp`) — only for drafting migrations |
| `STORAGE_DRIVER=s3`      | plus `S3_BUCKET=uploads` and Neon's `AWS_*` storage block     |
| `TEST_DATABASE_URL`      | local `fujisan_erp_test` — tests refuse any non-local URL     |

Workflow for a schema change:

1. `npm run db:new-migration -- <name>` drafts the SQL against the local Postgres and applies it there.
2. `npm run db:deploy` applies it to Neon (Render also runs `prisma migrate deploy` on every start).

Rules: never run tests, seeds with test data, or destructive SQL against Neon; tests only ever use
`TEST_DATABASE_URL`. Before any bulk change to Neon, back it up (Neon's server is newer than the
local `pg_dump`, so `\copy` each table to CSV, or use Neon's point-in-time restore).

## Railway instead of Render

Same settings: build `npm ci && npm run build`, start `npm run start:prod`, health check
`/api/v1/health`, and the same environment variables (generate `JWT_ACCESS_SECRET` yourself:
`node -e 'console.log(require("crypto").randomBytes(48).toString("base64url"))'`).
